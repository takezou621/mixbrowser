## 2. オープン課題(要決定)

| # | 課題 | 影響 | メモ |
|---|---|---|---|
| **Q1** | **「meta の muse」の正体と公式 API の有無**(Meta AI を指す? 別プロダクト?) | FR-2.3 / M3 の実装方式 | 公式 API 無しの場合は Muse もブラウザ連携アダプタになる。確定までスタブ |
| Q2 | 実装形態: Electron で開始するか、最初から Chromium fork か | 全体工数 | 本仕様は Electron 推奨(fork への移行パスは確保) |
| Q3 | 対応 OS | 開発・配布 | 推奨: macOS 先行、Windows 追従 |
| Q4 | 想定運用規模(アカウント数・日次投稿数) | 安全設定の既定値、レート抑制設計 | 例: 1〜5 アカウント / 1 アカウント日次 3〜10 件 |
| Q5 | 全自動実行モードの要否 | FR-5 | 推奨: M1 は承認ゲート固定 ON、M2 でオプトイン解禁 |
| Q6 | Claude Code の資産形態(ユーザー各自のサブスク前提か、API キーか) | FR-2.1、配布形態 | 本仕様は「ユーザー自身の環境を利用」を前提 |
| Q7 | 画像ソース(ローカルファイルのみか、AI 生成画像も対象か) | FR-3.1、ストレージ設計 | 生成画像を扱う場合は生成元アダプタの拡張が必要 |

## 3. リスクと軽減策

| リスク | 影響 | 軽減策 |
|---|---|---|
| x.com の DOM / data-testid 変更 | 投稿失敗 | アクセシビリティツリー観測、セレクタレジストリ(複数候補)、週次スモーク + 変更検知 |
| bot 検知 → アカウント制限 | 凍結 | 低頻度運用、実キー入力 + ジッタ、承認ゲート、headless 禁止、直列実行、日次上限 |
| 利用規約(自動化ルール)違反 | アカウント停止 | 同意画面、リスクの明示、公式 API ドライバという代替路の確保 |
| LLM 出力の品質 / 暴走 | 不適切な投稿 | 承認ゲート、文字数・内容バリデータ、ツール権限ホワイトリスト |
| ページ内テキストによるプロンプトインジェクション | 意図しない操作 | ページテキストは「データ」として注入、高リスクツールは人間承認必須 |
| セッション情報の窃取 | アカウント乗っ取り | OS キーチェーン、プロセス分離、エクスポート時の再認証 |
| LLM 利用料金の増大 | コスト | モデル選択の設定化、簡易タスクは小型モデル、トークン使用量の可視化 |
